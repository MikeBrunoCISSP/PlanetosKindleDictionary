## Context

See proposal.md for motivation. Confirmed by reading the actual code:

- **Request schema** (`packages/shared/src/entryImport.ts`): `importEntriesRequestSchema` deliberately uses `z.record(z.string(), z.unknown())` rather than `z.record(z.string(), z.string())`, with a comment explaining why — Zod would reject the *entire* request on the first bad value, contradicting "skip bad rows, don't fail the batch." Per-row shape checking happens by hand in the route. This shape stays the same; only what "by hand" checks for changes.
- **Route** (`apps/api/src/routes/entryImports.ts`): processes one row at a time, in its own `$transaction` per row (never batched) — the header comment explains this is a hard Postgres constraint (an aborted transaction poisons every later statement in it), not a style choice. Each row currently: checks `typeof rawValue === "string"`, validates the headword via `importHeadwordSchema` (`singleWordText`), sanitizes+validates the definition, then creates the `Entry` + one `SeriesWord` row, catching `P2002` as a duplicate.
- **Single-entry creation** (`apps/api/src/routes/entries.ts` lines 97-187) already does exactly what per-row import creation now needs to do, just for one entry per request instead of one per loop iteration: `createEntrySchema` (`packages/shared/src/entries.ts`) validates `inflections` with `singleWordText({ max: 200, ... })`, caps at `MAX_INFLECTIONS` (50), and `.refine()`s that no inflection duplicates the headword or another inflection (case-insensitive) — `DUPLICATE_WORD_MESSAGE`. The route then `tx.inflection.createManyAndReturn(...)` and folds the returned rows into one `tx.seriesWord.createMany(...)` alongside the headword's own `SeriesWord` row, inside the same transaction, so a `P2002` from *any* of them (headword or inflection) surfaces as one `DUPLICATE_WORD` error. This is the exact pattern to reuse per import row — not a new one to invent.
- **Client** (`apps/web/src/routes/entries/import.tsx`): `handleFileChange` does its own shallow shape check (top-level object, non-empty, under `MAX_IMPORT_ENTRIES`, `typeof value === "string"` for every value) and rejects the *whole file* client-side if that check fails — this pre-check exists purely as a fast, friendly fail before ever hitting the network; the server remains the real source of truth for content-level validation (duplicates, length limits, whitespace). The new client check mirrors this same depth: structural shape only (`Definition` is a string; `Inflections`, if present, is an array), not per-item content rules.
- **Layout**: confirmed with the user via an interactive mockup (three options compared) that the "Expected format" sample moves from side-by-side with the file picker to full width below it, since the new nested sample is both taller and needs more horizontal room for wrapped definition text.

## Goals / Non-Goals

**Goals:**
- Reuse `packages/shared/src/entries.ts`'s existing per-field inflection rules (`singleWordText`, `MAX_INFLECTIONS`) rather than reimplementing similar-but-different limits for import — but deliberately *not* reuse `createEntrySchema`'s all-or-nothing `.refine()` for the headword/duplicate check, since import's requirement is to clean up a bad inflection rather than reject the row (a considered divergence, not drift — see Decisions).
- Preserve the existing per-row, skip-not-fail architecture exactly as-is — only what gets checked and created per row changes, not the loop/transaction structure.
- Keep the clean break simple: no dual-shape acceptance, no migration shim.

**Non-Goals:**
- No changes to how duplicates are counted/reported — an inflection-caused duplicate is still just one more entry in `skippedDuplicateHeadwords`, identified by its row's headword. The only `ImportEntriesResultDto` addition is `droppedInflectionCount` (Decision 7), which exists solely to pick the completion toast's variant.
- No per-row or per-inflection detail in the response about *which* inflections were dropped or from which headword — the toast is a single, file-wide warning, not a diagnostic report (see Risks).
- No changes to `createEntrySchema`/`submitEntryEditProposalSchema` themselves — import calls the same validators, it doesn't modify them.

## Decisions

1. **Per-row validation** (`entryImports.ts`): replace the current `typeof rawValue !== "string"` check with:
   - `rawValue` must be a non-null, non-array object → else skip, reason "Value is not an object."
   - `rawValue.Definition` must be a string → else skip, reason "Definition is not a string." (same wording as today, since this exact reason string is already asserted in `entryImports.test.ts`).
   - `rawValue.Inflections`, if present, must be an array → else skip, reason "Inflections is not an array."
   - **Clean, don't reject, the inflections list**: filter `rawValue.Inflections` down to only the values that pass `singleWordText`'s own predicate (non-empty, no whitespace, ≤200 chars) *and* don't match the row's headword case-insensitively, then de-duplicate what's left case-insensitively (keeping first occurrence). Unlike `createEntrySchema`'s `.refine()` (which rejects the whole submission on any of these), this is a plain array filter/dedupe run before validation, not a validity check that can fail the row — nothing in this step ever produces a `skippedInvalid` entry.
   - *Then* check the cleaned list's length against `MAX_INFLECTIONS` → else skip, reason reusing `MAX_INFLECTIONS_MESSAGE`'s wording. This is the only remaining inflection-related row-skip condition, and it only fires post-cleanup (a row with 60 raw inflections, 15 of them junk/duplicates, is fine at 45 clean ones).
2. **Creation** (`entryImports.ts`, inside the existing per-row `$transaction`): after creating the `Entry`, follow `entries.ts`'s exact pattern — `tx.inflection.createManyAndReturn(...)` for the row's inflections, then one `tx.seriesWord.createMany(...)` combining the headword's `SeriesWord` row with one per returned inflection row. A `P2002` from any of them (headword or any inflection) is caught the same way as today and reported as a skipped duplicate for that row's headword.
3. **Revision snapshot**: change the hardcoded `inflections: []` (entryImports.ts line 117) to the row's actual created inflection values, matching what `entries.ts`'s own CREATE revision snapshot already records.
4. **Client validation** (`import.tsx`): replace `Object.values(entries).every((value) => typeof value === "string")` with a check that every value is a non-null, non-array object with a string `Definition` and, if present, an array `Inflections`. Keep the existing "reject whole file on any structural mismatch" behavior — this is a pre-flight fast-fail, not a content validator; content-level problems (duplicates, length, whitespace) still only surface after the server responds, exactly as today.
5. **`apiImportEntries`** (`apps/web/src/lib/api.ts`): its `entries` parameter type changes from `Record<string, string>` to `Record<string, { Definition: string; Inflections: string[] }>` (or an equivalent shared type from `packages/shared`, if one is introduced for the client-parsed shape — a plain inline type is sufficient here since the server keeps its own loose `z.unknown()`-based schema and doesn't need to share a strict type with the client).
6. **Sample + copy updates** (`import.tsx`): the "Expected format" `<pre>` block is rebuilt for the nested shape (see the pretty-printed sample already shown to and approved by the user), the legend gains a third dot for "inflections," and the page's intro paragraph is updated to mention inflections. The file-format section's row (`import-grid-row` / two `col` divs) becomes a stacked, full-width layout per the approved mockup (Option B): the file-picker block stays a compact row on top, the sample block moves below it at full width, instead of the current `flex flex-wrap` two-column row.
7. **Dropped-inflection signal** (`packages/shared/src/entryImport.ts`, `entryImports.ts`, `import.tsx`): `importEntriesResultDtoSchema` gains `droppedInflectionCount: z.number().int()`. The route accumulates it across the whole file — each row's cleanup step (Decision 1) adds however many values it removed (whitespace/empty/oversized/self-duplicate/in-row-duplicate) to a running total, initialized to 0 before the row loop. On the client, `onSuccess` branches on `result.droppedInflectionCount > 0`: build the same `parts.join(", ")` message as today, append `" - list truncated."` as today when `result.truncated`, then call `toast.warning(...)` instead of `toast.success(...)` when any inflections were dropped, further appending `" Not all inflections could be included."` — otherwise call `toast.success(...)` exactly as today. `sonner`'s `toast.warning` is an existing, standard API on the `toast` object already imported here; this is its first use in the codebase, not a new dependency.

## Risks / Trade-offs

- **[Risk]** Reusing `createEntrySchema`'s inflection predicates via ad-hoc reconstruction (rather than calling `createEntrySchema` directly) could drift from it over time — especially now that import's behavior on a duplicate/invalid inflection (silently drop it) deliberately diverges from manual creation's behavior on the same input (reject the whole submission). → **Mitigation**: import `singleWordText`/`MAX_INFLECTIONS` directly from `@planetos/shared` rather than re-deriving the limits as literals, and add a code comment at the filter site cross-referencing `createEntrySchema`'s `.refine()` so a future reader sees both behaviors are intentional, not an oversight.
- **[Risk]** Silently dropping a malformed inflection with zero signal would leave an admin believing every submitted inflection was imported when it wasn't. → **Mitigation**: addressed directly by Decision 7 — the warning toast (in place of a plain success toast) whenever `droppedInflectionCount > 0` gives an aggregate, file-wide signal. A remaining, accepted gap: the toast doesn't say *which* headwords or inflections were affected, only that something was; a future change could add per-row detail (e.g. surfacing it the way `skippedInvalid` already does) if that turns out to matter in practice.
- **[Risk]** This is a breaking, unannounced format change for anyone with an old-format export file already prepared. → **Mitigation**: explicitly out of scope per the user's own "clean break" decision; the rejection error message for an old-shape file should be clear enough ("must be a Definition/Inflections object") that the fix is obvious without a migration guide.

## Migration Plan

Purely additive to the codebase's shape, but behaviorally breaking for import files: no database schema change (entries/inflections already exist as tables), no feature flag — the old flat-string shape simply stops being accepted the moment this ships. Rollback is a plain revert; no data migration needed since import is a one-shot admin action, not a stored format.
