## Why

A dictionary's downloadable EPUB is only regenerated by the hourly change-detection sweep, so after an admin imports or edits entries there is no way to publish the result on demand from the UI. The backend already supports this - `POST /api/series/:slug/rebuild` is admin-only and forces a build regardless of whether content changed (build-automation's "Administrator Manual Rebuild" requirement) - but nothing in the web app calls it.

## What Changes

- Add an admin-only "Regenerate" action to the Dictionaries section of the app menu.
- "Regenerate" opens a searchable selection dialog, the same pattern as Update and Delete, whose first option is "All dictionaries", followed by each dictionary.
- Choosing a dictionary requests a rebuild of that dictionary and confirms that it was queued.
- Choosing "All dictionaries" requests a rebuild of every dictionary and reports how many were queued and how many failed.
- No backend, API, or database changes: the existing rebuild endpoint is reused as-is.

Non-goals: build-status or progress UI, a dedicated "rebuild all" endpoint, and deduplicating repeated manual rebuild requests.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `navigation/app-menu`: The Dictionaries shelf gains an admin-only "Regenerate" action with a selection dialog that includes an "All dictionaries" option.

## Impact

- `apps/web/src/lib/api.ts` - new `apiRebuildSeries` client function
- `apps/web/src/components/AppHeader.tsx` - Regenerate menu item, selection dialog, and toasts
- Relies on the existing `POST /api/series/:slug/rebuild` route (`apps/api/src/routes/downloads.ts`) and its tests (`apps/api/tests/downloads.test.ts`); neither changes
- No database schema changes; no new dependencies
