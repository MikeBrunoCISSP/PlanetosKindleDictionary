## Context

See proposal.md - Why for motivation. This design builds on three confirmed gaps in the current codebase: no cross-dictionary search or entries-listing endpoint exists anywhere, no case-insensitive/substring search pattern exists anywhere (no `contains`, no `mode: "insensitive"`, no raw SQL), and no pagination UI or `?q=`-driven route exists in the frontend (the only `validateSearch`/`Route.useSearch()` precedent is `login.tsx`'s `?mode=` tab pattern). It also builds on one existing piece of infrastructure that turns out to fit this use case precisely: `SeriesWord`, a model that already exists solely to enforce cross-table word-uniqueness (one row per headword, one row per inflection, all pre-lowercased via the existing `normalizeWord()` helper), which happens to unify "headword or any inflection" into a single searchable column.

## Goals / Non-Goals

**Goals:**
- Make `/` a fully public, no-auth search surface, replacing its current forced-login-redirect (which this change deletes, along with the now-obsolete `redirect-unauthenticated-to-login` change it came from).
- Establish this codebase's first case-insensitive substring search pattern, and its first ranked multi-word match, in a way that's fast at the app's expected data scale and safe under the project's parameterized-raw-SQL-only security rule.
- Keep the response shape simple enough that "which word(s) matched" can be computed in plain TypeScript rather than threaded through SQL.

**Non-Goals:**
- Full-text search over definition bodies (matching is headword/inflection only, per the proposal).
- Fuzzy/typo-tolerant matching, relevance scoring beyond "which query word matched first," or search analytics.
- A dedicated series/dictionary detail page — no such page exists yet, so the dictionary name in results is plain text, not a link.
- Cursor-based pagination — `SPEC.md` documents cursor pagination as a target, but no endpoint in the codebase actually implements it; this change follows the offset-based (`page`/`limit`/`skip`/`take`) pattern every existing list endpoint actually uses.

## Decisions

**Build the search query on `SeriesWord`, not on `Entry.headword` + `Inflection.value` separately.** `SeriesWord.normalizedWord` already contains every headword and every inflection value, lowercased, each linked back to its owning `entryId` (and, for inflection rows, `inflectionId`). Searching this one column means one query surface instead of two scans UNIONed together. Alternative considered: scan `Entry.headword` and `Inflection.value` independently and merge — rejected as strictly more complex for no benefit, since `SeriesWord` already does the unification and is already kept in sync at entry-creation time.

**Ranking requires a raw SQL query, not the Prisma query builder.** "Results matching an earlier query word rank above results matching only a later word" needs a per-row rank (effectively `MIN(word_index) GROUP BY entry`) that Prisma's builder can't express. This will be the app's first hand-written SQL, using Prisma's `$queryRaw` tagged-template form exclusively (auto-parameterized value interpolation via `Prisma.sql`/`Prisma.join`) — never `$queryRawUnsafe`, never string concatenation — to comply with `CLAUDE.md`'s "no raw/unparameterized SQL" rule, which is enforced by an ESLint `no-restricted-syntax` rule in `apps/api/eslint.config.js`. Shape: split the query into up to ~10 lowercased, LIKE-metacharacter-escaped words; `unnest(...) WITH ORDINALITY` turns that small word list into a driving table; join it against `SeriesWord` via `ILIKE`; `MIN(ordinal) GROUP BY entryId` produces the rank; join back to `Entry`/`Series` for display fields, filtered to `status = 'PUBLISHED' AND approvalStatus = 'APPROVED'`; `COUNT(*) OVER()` gets the total match count in the same round trip for pagination metadata. Alternative considered: N separate Prisma `findMany` calls (one per query word) merged and ranked in application code — rejected because it can't paginate correctly without over-fetching far more than 50 rows per word to compute a globally correct rank-then-offset, which is worse for both correctness and database load than one indexed SQL query with `LIMIT`/`OFFSET`.

**Match highlighting (which headword/inflection to bold) is computed in TypeScript, not in SQL.** The ranking query only needs to return, per page, which entries matched and in what order — not match provenance. After fetching the page's entries, a plain Prisma call (`inflection.findMany({ where: { entryId: { in: pageEntryIds } } })`) gets each entry's full inflection list; then each headword/inflection value is checked with a simple case-insensitive substring test against the same word list already computed for the SQL query. This keeps the raw SQL scoped to the one thing that genuinely needs a database-level query (ranking across a potentially large table) while the "what should be bold" logic — small-N, per-page, easy to unit test in isolation — stays in ordinary application code.

**A `pg_trgm` GIN index on `SeriesWord.normalizedWord` is required for substring search to stay fast.** No existing index supports `ILIKE '%word%'` efficiently (the only index on that column is a composite unique on `(seriesId, normalizedWord)`, usable for equality/prefix, not substring). `pg_trgm` is a standard Postgres contrib extension already bundled in the `postgres:16-alpine` image this project uses, so no infrastructure change is needed — only `CREATE EXTENSION IF NOT EXISTS pg_trgm` plus the index itself.

**Definitions are stripped to plain text via the existing `sanitize-html` dependency, not a hand-rolled regex.** `Entry.definitionHtml` is already sanitized on write to a narrow tag allowlist, so stripping it further (via `sanitize-html` with an empty allowed-tags list) is cheap and, importantly, handles HTML entity decoding correctly — a hand-rolled tag-stripping regex would not. Truncation is literal character-count (first 256 characters + "..." if longer), matching the requirement exactly, with no word-boundary smoothing.

**A dedicated rate-limit tier, not the existing read-endpoint default.** No public read endpoint in this codebase has a rate limit attached today (rate limiting is opt-in per-route). A public, arbitrary-input, cross-table-scanning search endpoint is more abuse-prone than a plain list endpoint, so it gets its own named, tunable constant rather than silently inheriting `SPEC.md`'s aspirational (and currently unenforced anywhere) 300/min figure.

**Frontend stays on `/`, driven by `?q=&page=`, rather than a separate `/search` route.** This matches the only existing search-param precedent in the app (`login.tsx`'s `?mode=`), keeps results shareable/bookmarkable, and gives back/forward navigation for free through the router's own search-param handling. `index.tsx` renders one of two layouts depending on whether `q` is present: a centered hero (reusing the existing `flex min-h-svh items-center justify-center` wrapper) with just the search box, or a top-anchored search bar plus the results grid.

**Search is submit-driven, not search-as-you-type.** Per direction, the search box does not fire a request on every keystroke — the query only runs when the visitor submits the form (Enter, or an explicit submit button rendered directly to the right of the input, labeled with a right-arrow icon rather than text). This is simpler than the debounce approach originally planned here: no debounce hook, no timer-driven navigation effect, no risk of a race between a debounce-triggered navigation and the user still typing. Local input state still syncs from the URL's `q` on external changes (e.g. browser back/forward) so the box reflects whatever query is actually active.

**Homepage identity content moves into the header dropdown, not a corner widget.** Per direction, `/` becomes pure search for every visitor. The existing `AppHeader`/`AppMenu` dropdown already exists and is only hidden for anonymous users at the top level (`{me && <AppMenu .../>}`) — adding a non-interactive username/email block plus a "Log out" item inside the existing "Settings" section is a small, low-risk addition to an already-established pattern, rather than introducing a new UI surface on the homepage itself.

## Risks / Trade-offs

- [This is the app's first hand-written SQL query, and every future edit to it needs care to keep it parameterized] → Confined to a single, small, well-commented query in one route file; the LIKE-escaping and parameterization are both covered by dedicated unit tests (see tasks.md).
- [Trigram-indexed substring search degrades for 1-2 character queries, since there are too few trigrams to be selective] → Accepted, documented limitation at this app's expected data scale (a crowd-sourced fan-dictionary app, not a search engine at web scale); not a blocker.
- [`COUNT(*) OVER()` computes the full matching set before applying `LIMIT`] → Fine at current/expected scale; worth revisiting if any single dictionary grows into the tens of thousands of entries.
- [A new rate limit (60/min/IP) is an untuned starting guess with no production traffic to calibrate against] → Kept as a clearly-named, easily-adjustable constant, not baked into shared logic.
- [This search relies on `SeriesWord` staying in sync with `Entry`/`Inflection`, which is only true today because entry edit/soft-delete endpoints don't exist yet] → Not a risk this change introduces, but flagged here so whoever implements entry editing next knows to keep `SeriesWord` in sync or search results will silently drift from reality.
- [Removing `/`'s auth redirect is a **BREAKING** behavior change for anyone relying on the current login-wall] → Intentional and directly requested; `SPEC.md` already documents anonymous browsing as a first-class requirement that the current redirect violated.

## Migration Plan

One Prisma migration: `CREATE EXTENSION IF NOT EXISTS pg_trgm;` plus a GIN trigram index on `SeriesWord.normalizedWord`. No data backfill needed (the column already exists and is already populated). Attempt to declare the index natively in `schema.prisma` via Prisma's extended-index syntax (`type: Gin`, `ops: raw("gin_trgm_ops")`) first, for schema-drift visibility; if that syntax doesn't validate cleanly against the installed Prisma version, fall back to a hand-authored `migration.sql` (via `prisma migrate dev --create-only`) with the raw SQL above, the same deviation pattern already used once this project for a migration Prisma's diff engine couldn't express non-interactively. Rollback is a straight `DROP INDEX`; no application code depends on the index existing for correctness, only for performance.
